Purpose

Ship triage-pg v1.0.1: give every problem_type a metric floor — a trivial/naive model whose score→rank→evaluate output (ADR-0010) sets the bar a real model must clear — and land the carried-over cloud/release hardening. Today only classification has baselines (catwalk/baselines/: BaselineRankMultiFeature, LinearRanker, SimpleThresholder). This milestone builds the missing floors for regression / regression_ranking / survival, plus the point-in-time-correct target-history data path the time-series baselines need — a real leakage boundary that earns its own ADR.

Problem

The score→rank→evaluate spine is already problem_type-agnostic and the in-PG metrics already cover all types (in_pg_evaluation.py: precision@/recall@/auc, rmse/mae/r2, c_index). So a baseline is "just another estimator." The catch: the most valuable regression baselines (persistence, moving average, seasonal naive, drift, Holt–Winters, Croston/SBA) all consume the entity's own prior target values — and the cross-sectional matrix (features + one forward label per (entity_id, as_of_date)) does not carry them. Exposing that history is a genuine point-in-time boundary: a target realized at date t over a label horizon w is only knowable at t + w. Feed it in one row too early and you leak the future into the "floor" — the exact failure the ADR-0009 fit-free/fit-based split exists to prevent, reappearing on the label side.

Solution

Land the work in eight phases ordered by risk × dependency. Phases 1–2 ship cross-sectional trivial floors (sklearn Dummy* + marginal survival) with no new data path — fast, low-risk wins that immediately give all four problem_types a floor. Phase 3 is the keystone: the point-in-time-correct target-history path (windowed-label lags + a raw-series sidecar) + ADR-0030. Phase 4 builds the time-series regression baselines on top of it. Phase 5 adds the pinball/quantile-loss metric so audition can honestly rank the quantile floors. Phase 6 wires floors into the example grids and ships the heavy GitHub-Pages docs. Phases 7–8 are the independent cloud/release-hardening and cosmetics tracks (parallelizable at any time). Every new baseline reuses the existing estimator seam (_fit_estimator/_score_column in adapters/model.py) and the existing in-PG metrics — no schema migration required.

Resolved Decisions

All six open questions were resolved with the maintainer on 2026-07-20. Recorded here as the settled contract the build follows; ADR-0030 (Phase 3) is the durable home for D1/D2/D5.

D1 — History source: reuse label projection for lags + a dedicated optional history_query for the raw series

Decision: the cheap lag baselines reuse labels._label_projection at prior as_of_dates (free, correct-by-construction). The raw periodic series that Holt–Winters/Croston/seasonal-naive need is a genuinely different quantity (period-level counts), so it gets its own optional history_query config key with its own knowledge-date discipline — decoupled from the forward label.

D2 — Exposure: reserved _target_lag_* columns for lags + a sidecar for the raw series

Decision: lags ride as reserved columns excluded from features, encoding, and both imputation passes (airtight ADR-0009 boundary; no real model trains on the label's own lags). The variable-length raw series rides as a sidecar keyed by (entity_id, as_of_date) handed to the estimator alongside X — columns would be a variable-width kludge. Regular-feature exposure was rejected (breaks the honest floor + corrupts structurally-missing history via imputation).

D3 — ETS/Croston dependency: statsmodels behind a new baselines extra

Decision: triage[baselines] optional extra with a guarded import; a missing extra raises "install triage[baselines]". persistence/MA/drift/promedio + Croston-core stay pure-numpy.

D4 — Activation: opt-in via grid_config

Decision: baselines are authored as class-paths in grid_config, exactly like today's classification baselines. No config-schema change beyond the optional history_query. Auto-injection (baselines: true) deferred to a later minor.

D5 — ADR ordering: ADR-0030 written first

Decision: write the decision boundary before building consumers (Phase 3 task 1). The target-history path is a hard-to-reverse data path; documenting it first prevents a leaky provisional shape from calcifying.

D6 — Constant-score ties: verify deterministic tie-breaking in Phase 1/2

Decision: actively assert precision@k is byte-identical across two runs of a constant-score baseline (Phase 1 task 4; re-checked for marginal survival in Phase 2). Fix the tie-order in prediction_ranking.py if not — an unstable floor metric would silently undermine the floor-vs-model comparison (ADR-0016 reproducibility).

Sharpest risks

The target-history leak is the single highest-severity correctness risk in this milestone. A baseline that quietly sees the future would lower the bar deceptively (an inflated floor), which is worse than no floor. The Phase-3 leak test (t + w ≤ as_of_date, checked against a synthetic fixture with known realized dates) is the gate — treat a red leak test as a hard stop on Phase 4.
  • Constant-score ties (Dummy, marginal survival) → confirm deterministic tie-breaking in the ranking spine (Q6), else precision@k floors wobble across runs.
  • Cold start — entities with < k history observations must degrade to a documented fallback, never a fabricated value.
  • Config-schema stability — keeping baselines opt-in via grid_config avoids touching the validated config surface at a patch release.
