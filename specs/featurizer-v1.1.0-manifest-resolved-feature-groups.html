Purpose

Two pieces of work, one landing. First, bump the featurizer pin from v1.0.1 to v1.1.0 and confirm the identity consequences are the expected, explained ones rather than silent drift. Second, use the API v1.1.0 adds — the queryable feature manifest — to close a dead end in our own code: explicit feature_groups.definitions globs are matched against physical column names, so any definition targeting an inner fragment of a long feature name aborts the run on every truncated column, with advice the user cannot act on.

The fix makes the obvious glob work, without importing featurizer into the pure module and without making feature grouping depend on cache state. It ships as v1.1.3, a patch on the 1.1 line, keeping v1.2.0 reserved for SHAP (ADR-0031).

Problem

src/triage/adapters/feature_groups.py:123-151 (_partition_explicit) globs the physical column name. A definition like {cardiac: ["*frecuencia_cardiaca*"]} therefore matches only the untruncated subset, and every truncated sibling raises: 

feature column 'COUNT(consultas.frecuen~1c0ca6e8' matches no
feature_groups.definitions glob; every column must belong to exactly
one group (add a glob or widen one).

On featurizer's own sample config that pattern hits 672 columns by label but 198 by column name. The remedy the message proposes — "add a glob or widen one" — is unactionable, because the tail has been replaced by a content hash nobody can predict or type.

Our own example hides this. example/dirtyduck/experiment.yaml:151-154 ships a commented definitions block using "facilities.*" and "*(inspections.*". Both match within the head of the name, which head-keeping truncation preserves — so they are truncation-safe by luck, not by design. Anyone copying that pattern and pointing it at an inner fragment hits the wall.
Not in scope: changing the truncation. featurizer measured and rejected tail-preserving truncation upstream (.out-of-scope/tail-preserving-truncation.md in that repo, with a test pinning the conclusion). We consume the shape as given. Nor do we match against definition as a label substitute: definitions embed truncated parent names and drop the interval, so P1W/P2W/P1M siblings are byte-identical.

Solution

Match explicit definitions against the label as well as the physical name, sourcing labels from featurizer's manifest. The load-bearing discovery — verified live during planning, not assumed — is where the manifest comes from:

Featurizer.feature_manifest reads self._plan, and planner.plan() runs inside Featurizer.__init__ (featurizer/featurizer.py:166) with no database connection. triage-pg always declares one-hot vocabularies in the config (adapter-spec §4 fixed-vocabulary path), so the manifest is fully determined by feature_config alone. Confirmed against example/dirtyduck/experiment.yaml with no DB in reach: 

manifest entries (no DB): 147     # matches the published 147-feature count
kinds: {'derived': 120, 'one_hot': 27}
truncated: 0
columns_matching("*(inspections.*"): 120

feature_groups.py stays pure exactly as its docstring promises — "no DB, no featurizer import". It gains an optional labels: Mapping[str, str] parameter defaulting to identity; the featurizer import lands in matrix.py, function-local, matching the existing pattern at matrix.py:218.

Questionables

The decision log. [asked] went to the maintainer; [decided] was settled by the agent with the rationale recorded; [unresolved] is still open with the assumption in force.

[asked] Which surface should explicit definitions globs match against?

Chosen: label, then column. A column joins a group if a glob matches its label or its physical name. Rationale accepted: it is a strict superset of today's behaviour, so no existing config can break — including one where a user hand-pasted truncated names, which is currently the only workaround. For untruncated columns the two operands are the same string, so the change is a no-op there. The alternative (label-only) is cleaner to explain and matches featurizer's own semantics, but would silently stop matching a hand-resolved glob.

[asked] What happens if the label map cannot be built?

Chosen: fail loud. Raise a ValueError naming feature_groups.definitions and chaining the underlying featurizer error. Rationale accepted: warn-and-fall-back-to-identity would make grouping depend on whether a plan build happened to succeed — the same class of environment-dependent behaviour as the v1.1.2 search_path bug, and against the repo's fail-fast rule. Only configs using explicit definitions can hit it.

[asked] Should there be a way to discover what a glob resolves to?

Chosen: --features on triage analyze-config. That command already inspects a config without a database, and the manifest is DB-free, so it is the natural home — one option plus a test, versus a whole new subcommand. It closes the loop: write a glob, see what it catches, before running anything.

[asked] How should this land, release-wise?

Chosen: v1.1.3 patch. Same shape as v1.1.1 and v1.1.2, keeping v1.2.0 reserved for SHAP per ADR-0031. The plan therefore carries a full release phase (version bump first, uv lock, doc re-captures, tag checklist, both release.yml jobs) rather than stopping at a green merge. The cache invalidation is user-visible and belongs in release notes rather than arriving unannounced.

[decided] Where does the label map come from — config, or threaded out of the featurizer run?

From feature_config, decided by the agent. featurizer's brief proposed threading a labels map from the caller in run.py and asked whether the manifest was available there. Investigation says: not from where they imagined. run.py:1142 takes feature_names off the built matrix, and the only Featurizer instance lives in _run_featurizer, reached only on a cache miss. A map sourced there would exist cold and vanish warm. But planner.plan() runs in Featurizer.__init__ with no DB, and triage-pg always declares one-hot vocabularies, so the manifest is fully determined by the config — verified live (147 entries for DirtyDuck, no database). This is strictly better than the proposed shape and needs no threading at all.

[decided] Build the map always, or only when definitions are present?

Only when present. group_by='source_entity' — the default and every tutorial config — is provably immune to truncation and never consults labels, so it should pay nothing for this feature. Building unconditionally would add a planner pass to every run for no benefit, and a wide config's plan build is not free.

[decided] Zero matches on --features: error, or empty answer?

Print "0 of N match" and exit 0. featurizer raises LookupError on an empty match, deliberately — but that is right for a selection API, where a silently empty selection is the failure being prevented. analyze-config is a diagnostic answering a question the user explicitly asked; "nothing matches" is the useful answer, and the user is most likely running it because their glob is not matching. Where we call featurizer's matcher we pass allow_empty=True and supply our own wording.

[decided] Does this warrant an ADR?

No. The three-part bar (hard to reverse · surprising without context · the result of a real trade-off) fails on all three: it is a reversible function-signature addition, unsurprising once the truncation is understood, and the rejected alternative was a bug rather than a road not taken. ADR-0023 gets a status line instead.

[unresolved] Does typer accept an optional-value option for --features?

Assumption in force: Click's is_flag=False, flag_value="*" passes through typer, giving both bare --features and --features '<glob>'. Not verified against this typer version. Phase at risk: 3, task 2 — cosmetic only. The fallback is specified inline (require the value; document --features '*' as the list-all form), so the phase cannot block on it.

[unresolved] Cost of the plan build on a wide config

Assumption in force: negligible — sub-second on DirtyDuck, once per experiment, against a DFS that takes far longer. Notes

Why the truncation is safe to leave alone

Head-keeping truncation is what makes group_by='source_entity' immune, and that is not a coincidence — the alias token sits at the front of every feature name, and the head is what survives. featurizer measured tail-preserving truncation upstream and rejected it as a regression, with a test pinning the conclusion. So the asymmetry is deliberate: the default grouping path is safe by construction, and only the explicit-glob path — which can target anywhere in the name — needs the label.

What this shares with the v1.1.2 bug

The v1.1.2 release fixed an unqualified results_schema_versions that resolved through the host role's search_path — correct in every database we own, wrong in a guest database. The shape recurs here in two places, and both shaped the design:

  • Our example config hides the bug. All three tutorial configs have 0 truncated columns and head-anchored globs, so the test matrix cannot see the failure — exactly as our benign search_path could not see the stamp bug. Hence the explicit truncation fixture in Phase 2: a test that fails without the fix.
  • The rejected design would have created a fresh one. Labels present on a cold run and absent on a warm one is the same defect class in a new location. That is the single strongest reason for the config-derived map, and it is why the cold/warm parity property is asserted in a test rather than left as a comment.
