Purpose

Work the post-v1.1.0 backlog to zero — but reconcile it first, because verification against the tree shows three of its seven items are already complete and one is a milestone masquerading as a chore. What remains after reconciliation is small and sharply defined: one CI line, one CLI flag, one release gate to watch, and one v1.2.0 scope decision. The reconciliation pass also surfaced work that was on no list — the repo-root README.md tells every new reader to docker pull …:v1.0.0-rc1, three releases stale — so this plan folds that in and extends the existing drift guard to cover the blind spot that let it survive.

Problem

The v1.1.0 release session named its own theme: silent staleness — "the thing still works, so nobody notices it's wrong." That session fixed three instances and added a guard for each. This backlog is the fourth instance, in both directions at once:

  • Stale in the optimistic direction — items stay on the list after the work ships. tutorial-smoke has run green for five consecutive nights; the triage score CWD-parquet fix shipped 2026-07-13/16 with tests; CONTRIBUTING.md was rewritten. All three still read as open, because the list they live on (CLAUDE.md's "Small seeds" paragraph) was never reconciled against TODO.org, which already marks them [X].
  • Stale in the pessimistic direction — docs keep asserting things the code stopped doing. README.md:12 still calls the cloud live validation "the gate between v1.0.0-rc1 and v1.0.0" (it ran 2026-07-19 and is what gated the release), and README.md:113 advertises the rc1 image tag. Both survived last session's sweep for one structural reason: the drift guard added then, test_docs_version_reference.py, scans only docs-site/src/content/docs/. The repo root was outside its blast radius.

The same structural gap exists in CI. The lint job runs uvx ruff check src/ — and [tool.ruff.lint] selects exactly three rules (F821/F822/F823), with no format --check at all. That is how a 10-file ruff 0.15.0 reformat rode into 092e2f43 unnoticed. The check is cheap and, verified below, would go green today.

Solution

Six phases, ordered so that the cheapest truth-establishing work comes first and nothing is built on an unverified premise. Phase 1 reconciles the backlog and closes what is already done — it changes the scope of everything after it, so it cannot come second. Phases 2–4 are the genuinely open construction work. Phase 5 is a release gate with no code. Phase 6 is a scope decision for v1.2.0, deliberately not an implementation.

The through-line matches the pattern the last release established and which this codebase now has a habit of: fix the instance, then add the guard that makes the class loud. Phase 2 guards format drift; Phase 3 guards doc-version drift beyond docs-site/; Phase 4 removes a standing manual runbook step so it cannot be forgotten.

[x] Phase 7: Document the per-as_of_date evaluation grain

Added 2026-08-05 after a maintainer question exposed a documentation gap. Not one of the original backlog items. Numbered after the gates only to avoid renumbering; it has no dependency on Phases 4–6 and is naturally executed alongside Phase 3, the other docs pass. Almost entirely documentation — the one exception is triage leaderboard --windowed in task 3, added by maintainer decision.

The problem

DSSG triage could not evaluate a model that was used at more than one prediction time. When a test matrix spanned several as_of_dates (any test_durations > 0day), the whole window collapsed into one number: predictions from every date were pooled into a single ranked list, so precision@100 over a month meant "of the 100 highest-scoring (entity, date) pairs anywhere in that month" — not "of the 100 we inspected each day". If you deploy daily at k=100 you actually inspect ~3,000 entities in a month, and the pooled top-100 answers a question no operator ever asks.

triage-pg already fixed this — migration 0010_windowed_evaluations (WS1, 2026-06-28), whose docstring names the defect verbatim: "evaluate a model at EVERY test as_of_date … instead of collapsing the test window into a single number at its max date" and "n_as_of_dates — the count the original triage couldn't give you." Three layers enforce it: ranks partition by (model_id, as_of_date) (0001:315); every metric function takes a required p_as_of_date and filters on it; the orchestrator loops over the distinct scored dates (adapters/model.py:953). as_of_date is in the triage.evaluations primary key, so per-date rows are the storage grain, not a view over something coarser. Behaviour is covered by test_model_builder.py:571 (test_evaluation_is_per_as_of_date).

So the gap is documentary, and it is real: n_as_of_dates appears in no markdown anywhere in the repo. evaluations_windowed is mentioned once, in docs/postmodeling.md, and nowhere on the published site. Meanwhile reference/configuration.md:197 shows test_durations: '0day' with no note that it yields exactly one evaluation point — so a reader copies the teaching default and never discovers the capability. The fix for the exact problem a user would hit is invisible to that user.

[x] Phase 8: Ontology layer — glossary terms + the Chicago 311 label-source leak

Added 2026-08-05 by maintainer decision, against the recommendation to defer this to its own milestone. Folding it in is the call; this phase scopes it honestly, including the consequence that makes it more than a doc edit.

The problem

An audit of the three tutorial DBs' ontology schemas against the intended shape — at least one entity table (static core attributes, one entity type per table) and at least one events table (involved entity, date, event type, attributes, ideally a location) — found DirtyDuck conforming and the other two diverging. Most of the divergence is defensible (both are transaction-grained problems where the unit of prediction really is the arriving item). Two findings are not:

  • CONTEXT.md defines 24 terms and neither Entity nor Event is among them — while triage.sources.role carries check (role in ('entity','event')) and several SQL functions branch on where s.role = 'entity'. The two nouns the whole entity_id spine rests on are undefined in the glossary that exists to define exactly that.
  • Chicago 311 carries closed_date and status on ontology.entities (03_create_ontology.sql:39-40) — they are the label source, i.e. the future being predicted. The only thing keeping them out of the feature set is that no config declares them. The guard is a comment, not a constraint.

1. Glossary: Entity and Event — the full definition low risk

Decision (maintainer, 2026-08-05): state the fuller definition, including the jsonb attribute bag and the spatial coordinate, rather than the minimal descriptive form. The glossary should say what the ontology layer should look like, not merely what the three tutorials happen to do — DirtyDuck is the only conforming one, and a glossary that describes the average of three schemas would enshrine the divergence.

  • [] Add Entity to CONTEXT.md: the object of interest an entity_id names — one entity type per table, described by the static "core" attributes that identify who or what this is, not by things that happened to it. Include the validity/state requirement (a daterange or an entity_state table): "who was in the population at time t" belongs in the schema, indexed, not re-derived in every cohort query. DirtyDuck's activity_period + GIST index is the reference.
  • [] Add Event: something that happened at a point in spacetime, carrying — the involved entity; when; a type discriminator; the event's own attributes, ordinarily a jsonb bag; and, where the data allows, a spatial coordinate (geography(Point,4326) + GIST, not untyped lat/lon doubles). Place the coordinate on the event whenever the event can move; on the entity only when it provably cannot (a facility does not relocate; a 311 request's location is the event's).
  • [] State the two clocks inside the Event definition: occurrence time (when it happened) and knowledge time (when it became observable to us). triage.sources.knowledge_date_column already encodes the second, and all three tutorial DBs currently collapse them into one date — silently asserting zero recording lag. Where the lag genuinely is zero, that should be written down, not implied by a missing column.
  • [] Add the promotion rule as a companion note inside the Event term, not as a replacement for the jsonb clause: promote to a typed column anything you intend to featurize; keep jsonb for what you retain but do not model. Rationale in one line — jsonb costs the type system and the planner's selectivity estimates, and featurizer's DFS consumes columns. DirtyDuck is the worked example: type/risk/result are typed ENUMs and are the declared features, while violations jsonb is (today) read only by label queries. Both halves of the rule matter; stating only the jsonb half invites a schema nobody can featurize.
  • [] Name the transaction-grained pattern explicitly: when the unit of prediction is the arriving item (a DonorsChoose posting, a Chicago 311 filing), the entity legitimately is an event — but the durable actors it references (teacher, school, community area) still belong in their own entity tables rather than as bare text columns. Two of three shipped tutorials are this shape; without the term a reader concludes they are bugs.
  • [] Cross-link both terms to the existing Source term (a declared input table whose role is exactly entity or event), so the glossary and triage.sources.role's check constraint agree.

[x] Phase 9: DirtyDuck violation features — structured first, text in SQL

Added 2026-08-05. Direct application of Phase 8's promotion rule to the dataset that most obviously needs it. This phase deliberately does not use featurizer's NLP bridges; task 3 records why, so the idea is settled rather than re-proposed.

The problem

ontology.events.violations — a jsonb array of {code, severity, description, comment} per inspection, with two GIN indexes — is the record of what inspectors actually found. It is used as a feature in zero configs. Grepping all eight DirtyDuck configs, violations appears only inside label queries (jsonb_array_length(violations) for the regression variants) and in a source description: string. The declared event features are result, risk, type — the inspection's verdict, never its content.

"How many critical violations has this facility accumulated in the last 3 months" is very likely the strongest unused signal in the dataset, it needs no new dependency, and it is exactly the feature a health department would reach for first. The published tutorial currently tops out at auc_roc 0.5751 against a 0.500 floor — a thin margin that makes "the ML barely earns its complexity" the lesson. Whether violation-content features move that is a genuinely interesting teaching result either way.

1. Structured features first — the cheap, high-value half

Two facts from dirtyduck/food_db/03_create_violations_table.sql shape this and should be stated in the config comments so nobody re-derives them: severity is a deterministic function of code (1–14 → critical, 15–29 → serious, else minor — lines 12–17), and description is the canonical text for that code, i.e. 1:1 with it. Anything derived from description as free text is therefore provably redundant with counting codes.

  • [] Project the jsonb into typed columns on ontology.events: n_violations, n_critical, n_serious, n_minor. featurizer then aggregates them (SUM/AVG/MAX) over the existing P1M/P3M/P6M intervals through the facilities → inspections relationship already in the config. Solves: the dataset's richest signal is unreachable to a DFS engine that consumes columns.
  • [] Optionally expose code as a categorical with a fixed vocabulary (top-N), following the pattern facility_type already uses — featurizer v0.4.0 fixed-vocabulary one-hot, so the matrix adapter's ordinal encoder does not fire on it.
  • [] Keep the violations jsonb column as-is. It stays the retained long tail; the counts are the modelled promotion. This is Phase 8's rule demonstrated on real data.

2. Text — in PostgreSQL, not through a bridge

The only genuinely free text is comment (the inspector's specific observation); description is code-determined, per above. The right tool is the one already installed: dirtyduck/food_db/00_create_extensions.sql loads pg_trgm, fuzzystrmatch and unaccent with the comment "kept for potential violation-description / fuzzy-match features (deferred, DB-audit #5/§7)". This phase is that deferral coming due.

  • [] Add a small set of boolean/count columns over comment for a fixed keyword set — rodent/mouse, roach/insect, temperature, handwashing — via tsvector or plain ILIKE. Dependency-free, PostgreSQL-native (the workspace's PostgreSQL-First rule), and pedagogically excellent: "did a prior inspection mention rodents" is a feature any reader immediately understands.
  • [] Keep the keyword list short and comment why each term is there. A long list overfits this dataset and turns a teaching feature into a leaderboard trick.
  • [] Leakage check, same as every other event feature: these aggregate over prior inspections through the existing as_of relationship, so the strictly-before boundary applies unchanged. The current inspection's own violations must never enter its own row.

3. Why NOT featurizer's NLP bridges — record the reasoning

featurizer v0.9.x does ship a text family and the pin (v1.0.0) includes it, so the capability is real. It is the wrong instrument for this text, on two independent grounds — both worth writing down so this gets settled once.

  • [] Signal mismatch. The Path-1 bridges are SentimentBridge (lexicon valence), ReadabilityBridge (Fernández-Huerta / Flesch), LanguageIdBridge, NERCountsBridge (spaCy persons/orgs/locations/money/dates). Against templated English regulatory prose: sentiment measures nothing (this is not opinion text), the readability of inspector boilerplate is not a facility-risk signal, language ID is a constant — a zero-variance feature — and NER has almost nothing to find (no persons, money, or organizations in a violation comment) while pulling in spaCy. The bridges are built for narrative text: case notes, complaint free-text, social media. Violation comments are none of those.
  • [] Operational mismatch. Per docs/featurizer-passthrough-features.md, triage-pg does not orchestrate bridge materialization: "run it as a Dagster/Snakemake asset (or a one-off) before triage run, then point the config at the result." DirtyDuck's entire promise is a two-command end-to-end run; a mandatory pre-step outside the pipeline breaks the tutorial it is meant to enrich.
  • [] Record both in docs/featurizer-passthrough-features.md (or .out-of-scope/ if it reads as a rejected feature) so "why don't we use the text bridges on DirtyDuck?" has a written answer. Solves: a plausible-sounding idea that would cost a dependency, a pre-step, and a tutorial's simplicity for near-zero signal.

4. Ship it without breaking the published tutorial

Verified constraints. Adding features does not change the experiment hash — features vary per Run, not per Experiment (ADR-0022) — and the nightly smoke's four assertions (b9e38fd8…, models=32, predictions=430176, evaluations=192) would all still pass.   • [] Use feature_groups (ADR-0023) in the new config — it is already present as a commented-out block in experiment.yaml:141-149. group_by: source_entity + strategies: [all, leave-one-out] yields one Experiment and several Runs whose leaderboards compare directly, answering the tutorial's own question: do violation-content features add lift over facility attributes and inspection verdicts? 2026-08-05T02:47-06:00 — added Phase 7: document the per-as_of_date evaluation grain

What changed. New Phase 7 (docs-only, plus one example config), three new entries in Relevant Files, two new global validation commands, and two new Questionables (page placement; whether triage leaderboard should surface n_as_of_dates/value_stddev).

Why. A maintainer question — "old triage couldn't compute metrics when a model was used for more than one prediction date; how are we handling it?" — turned out to have a good answer in the code and no answer in the docs. Verification found the behaviour correct and tested since migration 0010_windowed_evaluations (WS1, 2026-06-28): ranks partition by (model_id, as_of_date), every metric function requires an as_of_date, the orchestrator loops over scored dates, and test_model_builder.py:571 proves it. But n_as_of_dates appears in no markdown in the repo, evaluations_windowed is mentioned once outside the published site, and reference/configuration.md:197 shows test_durations: '0day' with no note that it yields exactly one evaluation point. A user therefore cannot discover the fix for the problem they have — which is exactly why the question was asked.

Constraint discovered while scoping it. The obvious move — change the tutorial's temporal_config to demonstrate a multi-date window — is blocked: tutorial-smoke.yml:97-112 asserts experiment_hash begins b9e38fd8, and temporal_config is part of Experiment identity (ADR-0022), so the edit would turn the nightly red and invalidate every published tutorial number. Phase 7 ships a separate experiment-cadence.yaml instead and states the constraint explicitly so a future reader does not rediscover it the hard way.

Ordering note. Phase 7 is last only to avoid renumbering Phases 4–6; it depends on nothing after Phase 1 and pairs naturally with Phase 3, the other documentation pass.

2026-08-05T13:22-06:00 — Phase 8 glossary states the full definition; Phase 9 added (DirtyDuck violation features)

Glossary (Phase 8 task 1) rewritten to the fuller definition, per maintainer instruction. The Event term now carries the jsonb attribute bag and the spatial coordinate as part of the canonical shape (with the coordinate on the event where the event can move), plus the two clocks and the transaction-grained pattern; Entity now carries the validity/state requirement. The earlier draft described only what the three tutorials happen to do — since DirtyDuck is the sole conforming one, that would have enshrined the divergence. The promotion rule (typed columns for what you model, jsonb for what you retain) is kept as a companion note inside the Event term rather than as a substitute for the jsonb clause: stating only the jsonb half invites a schema nobody can featurize.

New Phase 9, from the maintainer's question about text features. Investigation changed the shape of the answer. ontology.events.violations is used as a feature in zero configs — it appears only in label queries — so the real gap is not a text gap: the dataset's record of what inspectors found never reaches a model, while result/risk/type (the verdict) do. Phase 9 therefore leads with structured counts (n_critical/n_serious/n_minor), which need no dependency and are a direct application of Phase 8's promotion rule.

The NLP bridges are explicitly declined, with the reasoning recorded (task 3) on two independent grounds. Signal: the Path-1 family is sentiment / readability / language-ID / NER, and against templated English regulatory prose sentiment measures nothing, readability of inspector boilerplate is not a risk signal, language-ID is a zero-variance constant, and NER finds almost nothing while pulling in spaCy. Operational: docs/featurizer-passthrough-features.md states triage-pg does not orchestrate bridge materialization — it needs a Dagster/Snakemake pre-step, which breaks DirtyDuck's two-command promise. Text is still in scope, but in PostgreSQL: pg_trgm/unaccent are already installed with a DDL comment reserving them for exactly this, and keyword flags over the inspector comment field are dependency-free and pedagogically clearer.

Two verified facts drive the phase's constraints. (1) severity is a deterministic function of code and description is that code's canonical text (03_create_violations_table.sql:12-17) — so text-featurizing description is provably redundant with counting codes. (2) A source fingerprint is (row_count, max_knowledge_date) (sources.py:143), so adding columns changes neither and the derivation DAG would serve a pre-column matrix from cache — the version_label bump is a correctness requirement, not bookkeeping. Containment mirrors Phase 7: a new experiment-violations.yaml rather than editing the canonical config, because dirtyduckling.md publishes literal leaderboard values that the nightly smoke does not assert.
