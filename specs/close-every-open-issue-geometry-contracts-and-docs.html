Purpose

Close issues #10, #11, #12, #13, #14 and #15 — every open issue on the repository. All six were filed by the HockeyPredicts rebuild against v1.1.5 and all six were independently verified against the source in this session; none is a misreading of the documentation.

The work divides cleanly. Three are defects that produce a wrong or missing result with no error (#14, #12, #11). Two are surfaces that were never built — a production cohort for forward scoring (#10) and a date window for model selection (#13). One is documentation that describes a source checkout as though it described an install (#15).

Problem

The centre of this plan is #14, and it is worse than reported. A model is fitted on one column order and forward-scored on another. Nothing raises, because the column sets are identical and _design_X checks only for missing columns before calling frame.select(feature_names), which happily reorders.

The reporter traced it to feature groups (ADR-0023). It is broader than that: run.py:759 sorts the columns even when the config declares no feature_groups block, so every experiment whose matrix build order is not already sorted is affected. The reporter measured a max scoring error of 0.7420 on an MLPClassifier and 0.2895 on a logistic baseline over a ten-column rotation.

The finding that reshaped this plan. The issue's preferred fix — read the geometry from triage.model_groups.feature_list — is correct for models built by triage run and wrong for models built by triage retrain. retrain.py calls build_matrix with no feature-group projection at all, so build_model records and fits on the matrix's build order. Because _model_group_hash sorts the list before hashing, that retrained model rejoins the group whose stored feature_list is the original sorted order. Adopting the issue's fix unmodified would repair every run-path model and silently break every retrained one — which is currently, by accident, the only scoring path that is right.

The remaining five are smaller but each has the same shape — something the configuration declares that the system quietly does not honour:

Solution

Record each model's fit geometry on the model row, at the moment it is fitted, and read it back when scoring. triage.models gains a nullable feature_list text[] written by build_model from the order it actually passed to fit, so the run path and the retrain path each record the truth about themselves and predict_forward stops having to guess which stored list to believe. Existing rows are backfilled from triage.runs.purpose, which distinguishes the two paths exactly.

In the same phase, retrain.py starts projecting onto the group's recorded feature list before build_model, so a retrained model is fitted on its group's spec rather than on every column of the matrix — and rejoins its group for the right reason instead of because the hash sorts both lists.

The other five are local and additive. A boolean cast before the numeric guard (#12); a regex that strips a quote pair around the placeholder so both spellings render identically (#11); an identity-neutral cohort_config.forward_query with a CLI override and an ADR (#10); two defaulted date parameters on audition_pick and selected_model (#13); and documentation plus a placeholder page that names the two commands a reader needs (#15).

Because everything is on one branch, the Alembic ordering is a file-level fact rather than a merge-order constraint: 0022 sets down_revision = "0021_model_feature_geometry" and Phase 5 simply comes after Phase 1 in the sequence. Run just alembic heads before opening the PR — one head, not two.

Definition of Done

gh issue list on ccd-ia/triage-pg returns nothing, and each of the six issues was closed by the merge of a pull request that carried a test failing without its fix. A model forward-scored through triage score produces the same numbers as the estimator applied by hand to its own recorded column order, whether that model came from triage run or triage retrain; a boolean column declared in a featurizer config appears in matrices.feature_names; the same {as_of_date} spelling works in a cohort, a label and a subset query; a forward score can reach an entity whose outcome has not happened yet; an audition can be restricted to a date window; and a reader who installed from git knows why their dashboard is blank before they open a browser.

The numbers that make it checkable. Scoring error: the reporter measured a max absolute difference of 0.7420 (MLPClassifier), 0.4189 (LGBM) and 0.2885–0.2965 across four more groups when scoring through matrices.feature_names; after this plan the equivalent check is 0.0 for every group, asserted exactly rather than within a tolerance, because the same column order through the same estimator is the same arithmetic. Feature count: the reporter's five boolean flags went from dropped to present, and their workaround's 141 one-hot columns collapse back to the 136 the config declares. Test coverage: src/tests/adapter_tests/test_forward.py currently has three tests and zero references to feature_names or feature_list — which is why this shipped — and must not return to zero. Migrations: two new revisions, 0021 and 0022, each round-tripping upgrade → downgrade → upgrade on a copy of a real v1.1.6 database. Dashboard: the published wheel's triage/dashboard/static/ holds the built SPA rather than the 620-byte placeholder, and a page served from it carries <script> tags — the reporter's nine screenshots had zero.

Not included. No SHAP — ADR-0031 moves to v1.3.0 and keeps its own milestone; no change to the ADR-0022 experiment hash, which every phase must leave untouched; and no rewrite of _design_X into a strict order-checking API, which would be the belt-and-braces version of Phase 1 and is deliberately left for a follow-up. The release itself is gated on featurizer's own version bump: phases 1–6 are done when they merge, but this plan is not done until v1.2.0 is tagged against the new featurizer pin.

Questionables

[asked] #14 — where should the ordered fit geometry come from?

Chosen: persist per-model. A new nullable triage.models.feature_list text[], written by build_model from the order actually fitted and backfilled from triage.runs.purpose. The question was asked because investigation showed the issue's own preferred fix (model_groups.feature_list) is correct for the run path and wrong for the retrain path — it would have repaired one set of models and broken another, in a way no test currently covers. The cost is one migration and a backfill; the benefit is that neither caller has to infer which stored list to believe.

[asked] Does retrain's missing feature-group projection belong in this plan?

Chosen: fix it here, in Phase 1. retrain.py contains no reference to feature groups at all, so retraining a model whose group is a subset trains on every column. It is unreported, it is the same class of defect as #14, and separating them would mean writing the geometry tests twice. No new issue is filed; the PR body explains the extra scope.

[asked] #11 — which {as_of_date} contract wins?

Chosen: accept both spellings. Strip a quote pair immediately around the placeholder, then render quoted as cohort and labels do. The alternative of making subsets match cohort outright would break the Chicago 311 tutorial we ship, which teaches the quoted form; the alternative of validating and rejecting keeps the asymmetry that caused the issue. Normalising is strictly widening — there is no legitimate bare rendering, since it is always a syntax error.

[asked] #10 — how should the production cohort be expressed?

Chosen: identity-neutral config key plus a CLI override (cohort_config.forward_query and --cohort-query), with ADR-0032 recording why the key stays out of the experiment hash. The config key makes the production cohort a property of the problem and puts it in the artifact DAG; the flag covers the one-off without forcing a config edit.

[asked] #15 — ship the built SPA in the wheel, or document?

Chosen: a hatchling build hook that ships frontend/dist in the wheel, overriding the documentation-only option this plan first proposed. The objection raised at the time — that a build hook needs node at install time — was heard and overruled, so Phase 6 builds the bundle rather than explaining its absence. The objection is answered rather than ignored: the hook reuses an existing frontend/dist before attempting a build, which covers CI and the Docker frontend-build stage, both of which already produce one.

[decided] …and what the hook does with no node and no prebuilt bundle

Decided: warn loudly and ship the placeholder, rather than failing the build. A sub-decision the override did not cover. Hard-failing would turn today's blank-looking dashboard into a failed install for a node-less machine — a worse outcome for the very reporter who filed #15, and the wheel still carries the SPA on every normal path (CI, Docker, a developer machine with node). Hard-failing instead is a one-line change in build_frontend.py if that is preferred; say so and Phase 6 task 2 flips.

[asked] One pull request, or one per issue?

Chosen: a single pull request closing all six, against the per-issue split this plan first proposed on the strength of CONTRIBUTING.md rule 3. One branch, one CI round, one review. Two consequences are designed around rather than accepted silently. First, the merge stays a rebase and the branch keeps one commit per phase, so each Closes #N lands on main individually and git bisect still works across a change this wide. Second, rule 4 makes the PR title the release line and there is now only one title, so the PR body carries the six-issue breakdown a reader would otherwise get from six titles.

[asked] Phase 1 does not add a strict order-checking API to _design_X

The tempting belt-and-braces move is to make _design_X refuse a geometry it cannot verify, or to store a hash of the ordered list and assert on it. Once the fit order is recorded per model and read back directly there is nothing left to cross-check it against, so the assertion would compare a value to itself. The regression test is the guard. Put to the user and confirmed: no runtime assertion, no feature_list_sha256 column, no change to _design_X's signature. Recorded here because a reviewer will reasonably ask.

[asked] Which tag ships what?

Chosen: one v1.2.0 carrying all six issues, with SHAP (ADR-0031) moving to v1.3.0 — so TODO.org's milestone gets renamed in Phase 7. The cost, named when the question was put and accepted: the critical wrong-predictions fix does not ship until the audition migration and the forward-cohort ADR have also landed. A single tag means one release-notes pass and one verification pass.

[asked] The release waits on featurizer's own version bump

Constraint added mid-plan: featurizer is releasing a new version, and pyproject.toml pins it to a git tag (currently v1.1.0, ADR-0008/0016). Phase 7 therefore takes the featurizer bump first — pin, lock, re-quote the pin in CONTRIBUTING.md, and verify the bump by reading its changelog against this codebase rather than by a green suite — and only then tags v1.2.0. Blocks: Phase 7 alone. Phases 1–6 merge regardless.
